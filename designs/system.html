The saved cursor now advances only after a complete event. A reconnect resumes the existing reply rather than creating a second one.


What changed


The stream reader keeps an unfinished frame in memory and commits its cursor when the frame terminator arrives.
The display can still show partial text immediately. Persisting the cursor and displaying text are separate operations,
so a slow connection does not make the reply feel stalled.


Tool output stays attached to its original call. When a connection drops halfway through a result, the next connection
resumes that result using its call ID. We no longer create another tool row for the same call.


Checks


I replayed a disconnect before the first token, between text fragments and during a tool result. The partial answer
stayed visible each time. Repeated events did not duplicate text, and a final result arriving twice completed the turn once.


The longer replay includes text, a file read, a command result and another paragraph after the tool finishes.
Each interruption resumes the same sequence. The tool's expanded state stays with its original call, so opening the
result before the reconnect does not create a second disclosure or close the one you were reading.


I also left the chat scrolled halfway through an earlier answer while the replay continued. New text arrived below
the reading position. Returning to the end showed the complete reply with the same cursor boundary. A queued message
started after that reply finished, without replacing its text or borrowing its tool results.
