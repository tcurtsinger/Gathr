# Run Gathr

Part of [AGENTS.md](../AGENTS.md)'s Run, use and check it; the other parts are listed there.

- **The crate:** `crates/gathr` holds the shared library and two binaries: `gathrd`, the service, and `gathr`, the command line. Service code is in `src/bin/gathrd/`, command-line code in `src/bin/gathr/`, and what both use in `src/`.
- **Start it with test data:** `cargo dev --port <port> --data <folder> --seed` builds both, adds the made-up chats (500 messages, 50 tool calls in a turn, a 20,000-word answer, and a team of five over 20 rounds: tasks, hear-backs, reviews and a late reply, on a made-up account "Seed team", and six open questions for the person across two chats, one of each answer form, three with files) and starts the service. Ctrl+C stops it and everything it started. `cargo dev` and `gathr seed` refuse to run without `--data`, so made-up data never reaches the installed Gathr's own folder. Its agent folder is beside the data folder, `<data>-agents`, as for every data folder but the system's own, so made-up projects never reach the person's own `~/Gathr`.
- **With the window:** add `--window` to `cargo dev`: it also starts the UI's dev server on the port plus 10 and the desktop window on it, and Ctrl+C stops them too. A browser can open the same address (`http://127.0.0.1:<port + 10>/`). The dev server adds the service's token to every `/api` request, so the page never holds it. Its window's title says `Gathr (dev <port>)`.
- **Without a login:** `examples/replay_engine.rs` stands in for Claude Code. Build it (`cargo build --example replay_engine`), start `cargo dev` with `GATHR_REPLAY` set to a recording in `crates/gathr/tests/frames` and `GATHR_CLAUDE_PATH` set to `target/debug/examples/replay_engine(.exe)`, add an account (`POST /api/accounts`), and put a made-up `.credentials.json` with an `accessToken` and `refreshToken` in its `<data>/accounts/<id>/claude`. Every send then plays that recording. A `{"dir": "sleep", "line": "<ms>"}` row in a recording pauses that long, for a stream at a real pace when timing.
- **Run it installed, without cargo or a dev server:** put `gathr-app`, `gathrd` and the built UI (`npx vite build` in `ui/`, then `ui/dist` copied as a folder named `ui`) in one folder, and open `gathr-app`. With no arguments it uses the system's app data folder (`--data <folder>` for a check), finds the service there or starts it, and signs in through a one-time link. The service runs from the data folder's own copy, `<data>/app/<version>/gathrd` with its `ui`, copied from beside `gathr-app` at first start and again when the installed one is newer or rebuilt ([0032](decisions/0032-service-updates.md)). `gathrd` serves the UI from the `ui` folder beside it (`--ui <folder>` for another). Closing the window hides it in the tray (the menu bar on macOS) and the service keeps running; opening Gathr again on the same data folder shows that window, starting the service again if it stopped. Quit in the tray stops both. Each data folder has its own window, so a check on a test folder never brings up the owner's. A service started this way never sees a `GATHR_*` variable, and one started with no `--port` never keeps a port from 47100 to 47114.
- **A browser on the service itself:** `gathr open --data <folder>` starts the service if it isn't running and prints a link that signs a browser in once (good for 60 s). On Windows, a service it starts inherits its output: send that output to a file, not a pipe you wait on.
- **Test data alone:** `gathr seed --data <folder>`, with the service stopped. Each run adds another set, so repeated runs make a large folder for timings.
- **No borrowed engines:** installed Gathr runs only its checked Claude Code/Codex copy. Before the first copy arrives,
  turns stay queued with "Claude Code is downloading" or "Codex is downloading", survive restart, and start after
  the copy passes its checks. Explicit `GATHR_CLAUDE_PATH` / `GATHR_CODEX_PATH` stand-ins remain for dev/tests;
  neither engine falls back to the person's PATH. To check: `cargo test -p gathr --test owned_engines --test engine_copies`.
- **A signed-in test account:** a new data folder has none. Add one in Settings (or `POST /api/accounts`) and sign it in there; its login lives in `<folder>/accounts/<id>/claude`. Never point Claude Code at `~/.claude`.
- **Codex recovery checks:** `cargo test -p gathr --test codex_recovery` covers service-gated wait checks (including Full and shutdown), rejected turn starts, and a completion racing a rejected steer. The service asks before saving a Codex check in Ask and Edits; in Auto it's Codex's reviewer's. Claude keeps its native hook.
- **Engine recordings:** the tests replay real Claude Code and Codex frames from `crates/gathr/tests/frames` through `examples/replay_engine.rs`, which `cargo test` builds. The `steps_*` files there are hand-written in the shape of real frames, not recordings, and say so in their first row ([0041](decisions/0041-what-a-step-ran.md)), as `exits_mid_reply` is. To record one, run the turn on a dev service, export its frames with the query in `scripts/scrub-frames.mjs`, run that script, and read the result for anything personal before committing it.
