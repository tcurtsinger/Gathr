# 0002. One login folder per account, shared by its agents through a renewal gate, never copied, never killed mid-renewal

Status: accepted. Date: 2026-11-06, revised 2026-11-07 (one folder per account, the owner's call).

## Implementation status

Named accounts, isolated login folders and per-account gates are built. The background login watcher and its renewal/change history are not built yet. Codex login state follows 0033, as clarified below; the expiry-based state is specific to Claude Code.

## Choice

- Each signed-in account gets its own engine folder under Gathr's data folder: `<data>/accounts/<account-id>/claude` passed as `CLAUDE_CONFIG_DIR`, or `<data>/accounts/<account-id>/codex` passed as `CODEX_HOME`. The person signs each account in once, through the engine's own login flow, inside that folder. An engine can have several accounts (a main and a second Claude login, say).
- Each agent picks one account. All agents on an account share its folder, so several engine processes can run on it at once, each agent with at most one ([0010, Sessions](0010-coordination-as-state.md#sessions)).
- **Claude renewal gate** (ported from the previous app's `renewalGate` in `drivers/claude-login.ts`, the owner's code). Every engine start and every turn sent to a running engine passes the gate of its account first. When the account's access token expires within 5 minutes, one of them goes ahead and its request renews the login; the rest wait, re-reading the login file every 250 ms, until the file shows a fresh expiry or 30 s pass. A start that is no longer wanted leaves the queue. Sign-ins and status probes take the gate the same way.
- Gathr retains only credential presence and expiry state while decoding a login file; credential values are discarded. It never copies a login file or uses the person's `~/.claude` or `~/.codex` login.
- Nothing of the person's own setup is copied into an account's folder, and engines don't load what their login brings into it ([0024](0024-only-what-gathr-gives.md)). What the person wants from Claude or Codex (skills, agents, commands, servers) is imported into Gathr and given to agents from there. Login files are never copied: Claude's `.credentials.json` and `.claude.json`, Codex's `auth.json` and `.sandbox-secrets`.
- Login state is read without starting a turn: for Claude, `claude auth status` (exits 0 signed in, 1 signed out, prints JSON) on macOS, and the presence and expiry fields of the login file elsewhere, never its tokens; for Codex, a nonempty refresh token or API key in the account's own `auth.json` (0033), without starting app-server. The following expiry states apply to Claude:
  - **signed in:** a login is there and its access token is current;
  - **stale:** the access token has expired but a refresh token is there. The engine renews it on its next request, so queued work is not held. The service runs a Claude probe (`claude auth status`) through the renewal gate, only when no engine on the account is mid-turn, and never killed. If one is, its next turn's result decides instead;
  - **signed out:** only when the login is gone or blank, a probe says signed out, or a turn fails with the engine's login-expired error (Claude: `Login expired · Please run /login`). Then queued work waits for a sign-in.
- The engine's environment is built, not inherited as is. Every variable that selects a credential or a provider is removed, and only the agent's own choice is put back (a key or provider the person set for that agent in Gathr):
  - Claude, following its [authentication precedence](https://code.claude.com/docs/en/authentication#authentication-precedence), where each of these outranks the folder's `/login`: the provider selectors `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, `CLAUDE_CODE_USE_MANTLE`, `CLAUDE_CODE_USE_ANTHROPIC_AWS` and `AWS_BEARER_TOKEN_BEDROCK`; `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_PROFILE`, `ANTHROPIC_FEDERATION_RULE_ID`; and `ANTHROPIC_BASE_URL`, which reroutes requests to a gateway. As a backstop, any other inherited `CLAUDE_CODE_USE_*` or `ANTHROPIC_*` variable is removed too, so a selector added in a later Claude Code release doesn't slip through.
  - Settings copied into the folder drop `apiKeyHelper` and any of the variables above from their `env` block, since settings can set them as well.
  - Codex: `OPENAI_API_KEY`, `CODEX_API_KEY` and `CODEX_ACCESS_TOKEN` ([Codex environment variables](https://learn.chatgpt.com/codex/config-file/environment-variables)). The driver also starts app-server with `cli_auth_credentials_store="file"`, so the login stays in `auth.json` in the account's folder rather than the OS keyring ([Codex auth](https://learn.chatgpt.com/codex/auth)).

Codex also passes the service's per-account start/turn gate, but Gathr does not read its token expiry. Codex manages its own renewal and `auth.lock`. A readable file with a nonempty refresh token or API key is shown as signed in; a missing/blank login is signed out. An unreadable or partly written file is `unknown`. Presence does not prove the provider will accept the login.

## Why

- **Refresh tokens are single-use.** Codex refreshes a token 5 minutes before it expires and a reused refresh token fails with `refresh_token_reused`, forcing a new sign-in (`codex-rs/login/src/auth/manager.rs` in [openai/codex](https://github.com/openai/codex); [Codex auth docs](https://learn.chatgpt.com/docs/auth): tokens live in `auth.json` under `CODEX_HOME` and refresh automatically). The previous app hit the same with Claude Code: two processes renewing at once, or one killed between renewing and saving, leave a spent token, and the next renewal blanks the login. Sharing an account's folder means managing that race, which the gate does at every start and turn.
- **One sign-in per account.** A dozen agents on two accounts is two sign-ins, not twelve, and switching an agent to another account is a setting, not a new login. This is how the previous app works and what the owner chose.
- **Codex already guards a shared folder.** It takes a file lock, `auth.lock` in `CODEX_HOME`, around every write of `auth.json`, "to serialize the whole read/modify/write across managers and processes"; before renewing it re-reads `auth.json` and skips the renewal when another process has already done it; and it refuses to save a renewal over a login that changed meanwhile ([storage.rs](https://github.com/openai/codex/blob/faeb379646bdbad016e11f7c9ca91113cad4bc9d/codex-rs/login/src/auth/storage.rs#L194-L213), [manager.rs, renewal](https://github.com/openai/codex/blob/faeb379646bdbad016e11f7c9ca91113cad4bc9d/codex-rs/login/src/auth/manager.rs#L3473-L3522), [manager.rs, save](https://github.com/openai/codex/blob/faeb379646bdbad016e11f7c9ca91113cad4bc9d/codex-rs/login/src/auth/manager.rs#L1757-L1781)). The re-read and the renewal aren't under one cross-process lock, so two processes can still both renew in a narrow window; the gate narrows it further.
- **Claude Code's renewal isn't public.** Its source isn't published and no doc says how processes sharing a folder renew. The previous app's evidence is that they can collide, so the gate applies to Claude in full.
- **The folder variables move the login.** `CLAUDE_CONFIG_DIR` moves settings, history and `.credentials.json` ([env vars](https://code.claude.com/docs/en/env-vars)); `CODEX_HOME` holds `auth.json` and `config.toml` ([Codex auth](https://learn.chatgpt.com/docs/auth)), and app-server reports the folder it uses as `codexHome` in its `initialize` response (generated schema, codex-cli 0.166.0).
- **Codex can sign in from inside Gathr.** app-server has `account/login/start` with `chatgpt` (returns an `authUrl`), `chatgptDeviceCode` and `apiKey`, and announces `account/login/completed` ([app-server docs](https://learn.chatgpt.com/docs/app-server)). Claude Code is signed in by running its own `claude /login` in that folder.
- **The environment outranks the folder.** Cloud provider selectors, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `apiKeyHelper` and `CLAUDE_CODE_OAUTH_TOKEN` all rank above a `/login` subscription, and in `-p` mode the API key "is always used when present" ([authentication precedence](https://code.claude.com/docs/en/authentication#authentication-precedence)). A person who starts Gathr from a shell set up for a gateway or a cloud provider would otherwise send an agent's requests on that credential while Gathr shows its own login.
- **Expiry isn't sign-out.** Claude Code's docs: "authentication keeps working until the login actually expires", and requests fail with `Login expired` only "once the stored login expires and can't be refreshed" ([renew an expiring login](https://code.claude.com/docs/en/authentication)). Holding work on an expired access token would stop an idle agent that would have renewed on its first request.
- **Ported from the previous app (the owner's code):** the folder per account, the renewal gate, settings copied in and logins never (`drivers/claude-folder.ts`, `drivers/codex-folder.ts`), reading login state from the file instead of starting Claude Code (`drivers/claude-login.ts`), and watching the folder, not the file, since Claude Code replaces the file when it saves, with a once-a-minute re-read because Windows can drop a change event (`login-watch.ts`). That watcher exists because a cleared login was once noticed 29 hours late.

## Rules that follow

- **Never force-kill an engine that may be renewing.** Stop and close go through the engine's interrupt (0001). A kill after the grace period is written to the event record with the agent, the process and why, so a lost login can be traced to it. This replaces the previous app's `engine-trail.ts`, which kept 10 minutes of starts and kills in memory for the same purpose.
- **Login changes are events.** Each move between signed in, stale and signed out is recorded with every engine process running on that account just before, and every renewal the watcher sees (the login file's expiry moving forward) is recorded too. When the watcher sees a login disappear, every agent on the account shows as signed out and their queued work waits; when it sees one expire, they show as stale and a probe follows (above).
- **The shared-folder risk is measured, not assumed.** The Diagnostics page shows, per account, the sign-outs with the engine processes running at each, the engines' own login errors (such as a refresh token already used), and the renewals the watcher saw. That last count is a floor: two renewals between the watcher's reads look like one, so the watcher alone can't prove a collision. The sign-outs, the processes running at each, and the engines' errors are the evidence. If sign-outs keep following several agents running on one account, the remedy (for example, holding new turns on an account while one renewal is in flight) is a new decision with those numbers.
- **Status checks are never killed.** `claude auth status` may itself renew; the service waits for it to exit on its own (the previous app waited up to 30 s, then trusted the file).
- **An account folder is deleted only when the person removes the account,** after every agent on it has moved to another account or been deleted, and every process on it has exited.

## Named accounts in the service (2026-11-07, task 947)

- **Stored** in the `accounts` table: an id, its engine and a name. The folder is `<data>/accounts/<id>/<engine>`, named by id, so a rename never moves a login. Names are unique, ignoring case, so a picker never shows two the same. Turned down: folders named after the account, which a rename would have to move while an engine might be renewing in it.
- **No account until the person adds one.** Gathr is standalone: a new data folder starts with none, and each is added and signed in through Gathr. Chats run on the oldest account until agents pick their own (0026); with none, a message waits as it does signed out. When that account changes, chats start new Claude Code sessions, because a session lives in the old account's folder. Turned down: a ready-made "Main" account, which read as something brought in from the person's own Claude.
- **Sign out** runs the engine's own `claude auth logout` in the account's folder (2.1.318 removes `.credentials.json` and exits 0 in 0.4 s; on macOS it clears the Keychain entry, not verified), after the account's renewal gate, so it never lands under a renewal. Engines still running on the account aren't stopped: their next turn finds it signed out and waits. Turned down: deleting the login file ourselves, which can't reach the Keychain.
- **Remove** (task 990): chats move to the next account first, then every engine on the account closes the gentle way (a turn under way ends as stopped). With its renewal gate held to the end, a folder that exists is signed out as above, and the folder `accounts/<id>` is deleted, tried for a second while Windows lets go of a closed process's files, as the previous app did. Only then is the account forgotten. If the sign-out or the delete fails, the account stays and the error carries a reference. An account never signed in has no folder and goes without Claude Code. Turned down: forgetting the account when its folder won't go (the previous app's way), which leaves a folder nothing points to.
- **Codex accounts** are refused until the Codex driver exists; the table already takes them.

## Turned down

- **One folder per agent, each signed in separately** (this decision's first version, and the team's pick). Only one process ever renews each login, so the race can't happen; but every agent needs its own browser sign-in, a dozen for a dozen agents. Turned down by the owner on 2026-11-07.
- **The person's own `~/.claude` or `~/.codex`, so agents work with no sign-in.** This is how Open Design does it (read in its installed build, 2026-11-07): it starts Claude Code with no `CLAUDE_CONFIG_DIR` unless one is set in its Settings, so Claude Code uses `~/.claude`, and it sets `CODEX_HOME` to `~/.codex`. Every agent then shares one login with the person's terminal sessions and with each other, so they race for the same token; Open Design has its own `refresh_token_reused` error for when that happens. It also allows only one account per engine. Turned down by the owner on 2026-11-07, because it breaks using several accounts.
- **A long-lived token** (`claude setup-token`, one year, via `CLAUDE_CODE_OAUTH_TOKEN` ([authentication](https://code.claude.com/docs/en/authentication))). It avoids renewal entirely but is a copyable secret Gathr would have to store; kept as an opt-in for a later decision, not the default.
- **Gathr running the OAuth flow itself.** That would mean Gathr holding tokens; the engines' own flows keep the secret inside the engine's folder.

## The owner's calls

- **Subscription logins (2026-11-07).** Anthropic's Agent SDK page says: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" ([overview](https://code.claude.com/docs/en/agent-sdk/overview)). Gathr doesn't offer a login: it runs the person's own Claude Code, signed in by them in its own folder. The owner's call: Gathr runs on the person's existing subscriptions, as other apps do, and no approval is sought. Turned down: asking Anthropic for approval before a public release.
- **Gathr's own folders, not the person's (2026-11-07).** The owner asked whether agents could work with no sign-in, as in Open Design. Open Design shares the person's own login folders (see Turned down), which breaks several accounts, so Gathr keeps its own folders, "the way SerenityOS does it".
- **One folder per account (2026-11-07).** Asked to choose between one sign-in per agent and one per account as in SerenityOS, the owner chose one per account.

## Checked in the first slice

- `CLAUDE_CONFIG_DIR` moves `.claude.json` too: a fresh folder gets its own (Claude Code 2.1.318, Windows).
- A message sent while signed out waits, `gathr diag health` shows it held on the account, and it went out by itself once the folder was signed in.
- A refused login (Claude Code's `authentication_failed`) holds the account's work until the login file changes, rather than starting an engine every poll.

## Not verified

- Where keyless Console sign-ins are stored (the docs say outside the folder).
- How often agents sharing a Claude account collide on renewal. The first slice runs two agents on one test account across an access-token expiry and reads the renewal and sign-out events.
- Claude Code's own refresh timing isn't documented; the 5-minute figure is Codex's, and the previous app's observation for Claude.
- Whether `claude auth status` reports an expired-but-refreshable login as signed in, and whether it renews it. The probe is never killed either way.
- Which variables Codex app-server itself reads for credentials: the docs list `CODEX_API_KEY` for non-interactive runs and `CODEX_ACCESS_TOKEN` for automation, and give no precedence over `auth.json`. Removing them is safe either way.
