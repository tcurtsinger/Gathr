# The API: checks runs and merging

Part of [AGENTS.md](../AGENTS.md)'s Run, use and check it; the other parts are listed there. The API's address and sign-in are in [api.md](api.md).

- Review evidence (G165): a CI wake on a review task keeps its recorded done review. R covers H when they are equal, or every added first-parent commit is a two-parent merge whose first parent is the preceding accepted commit and whose other parent is on the fetched base. Each whole tree must match Git's clean automatic merge (`git merge-tree --write-tree`); author changes, conflicts and unsupported merge shapes need review again. Current-head checks still gate the merge. An explicit unfinished finish, cancellation or restart withdraws approval. A held review's owner can re-record done on that same task without changing its PR, dependencies or lifecycle. Upgrade preserves provably completed reviews; an ambiguous older held record needs that explicit refresh.

- Checks runs (0043 C3): Gathr runs a project's checks (C2b) at a commit in `<agent folder>/<Project>/checks`, a detached worktree of the project reset before each run (`fetch` from `origin`, `checkout --force`, `clean -ffdx`), so nothing left uncommitted anywhere, nor by an earlier run, reaches it. Caches are beside it in `<Project>/caches` (`CARGO_TARGET_DIR`, `npm_config_cache`, `PIP_CACHE_DIR`). One run at a time per project; commands run in order in `sh` (Git Bash on Windows), up to an hour each, stopping at the first failure. The PR looks start a run for an open review task's PR at each head they see that has none. `POST /api/projects/<id>/checks/runs {"head"}` starts one (409 for a project with no checks); `GET` lists the newest 50 (`?head=<commit>`: that commit's, however old), each with `head`, `state` (`running`, `passed`, `failed`), `why`, `ref` once failed, and `steps` (`command`, `exit`, `duration_ms`, the last 64 KB of `log`). `GET /api/projects/<id>/caches` answers `bytes`; `DELETE` removes them. A step whose result isn't saved fails the run (never a pass without its evidence). A run a stop of the service cut off ends failed at the next start, with its own `gathr.checks.end` so its reference traces, and doesn't count as run, so the PR looks run that commit again. Caches no run used for 14 days go with the service's looks (`GATHR_STALE_DAY_MS` shortens a day). Live `{"type": "checks", "project", "head", "run", "state"}`; events `gathr.checks.start`, `gathr.checks.end` (an error with why when it fails, so its reference traces) and `gathr.checks.caches`. Each task with a PR has `pr_head`, the head the PR looks last saw, so the window shows the run at that commit on the task: Summary's task list and a hand-off line's Open task open the task in the Tasks tab (owner's pick, room task 70), and Settings > Projects > Checks & merge shows the cache's size and Clear. Without GitHub, write a task's `pr_head` and the project's checks with the service stopped, then `POST …/checks/runs`.
- Merging (0043 C4): agents don't merge; a PR's reviewer calls `merge {"pr", "signed_off"}`, and Gathr refuses, with a reference, unless the caller owns a review of that PR in the chat recorded done on a commit R covering its head H (GitHub's `headRefOid`; the reviewed id, 7 to 40 hex characters, resolved in the project and a true prefix of R), the checks the project asks for passed on H (`ci`: GitHub's `statusCheckRollup`; `gathr`: the latest checks run at H passed, C3, and started after the checks were last set; `both`; `none`: no checks, the review alone, 0045), and the default branch's B (fetched from `origin`) is in H. The PR's head and base are read again just before the push and refused if either changed; after it, the tasks settle only once GitHub shows the PR merged at that head into that base (waiting up to 20 s, `GATHR_MERGE_CONFIRM_MS` shortens it in dev and tests), else the answer says it isn't shown merged, with a reference, and nothing settles; settling that fails after the merge is said the same way, and the PR looks settle the tasks once GitHub reports the merge. A PR changing tests or check settings (a `test`/`spec` path, `.github/workflows/`, `package.json`, `Cargo.toml`, `pyproject.toml` and the like), or bringing a project its first passing checks on main (no passed run at B or before it), also needs `signed_off: true`. One merge per repository at a time, by the project's `merge`: `fast-forward` pushes H to the base, `merge` pushes a merge commit of H onto B made with `git commit-tree` (as the checkout's own git user), `squash` calls GitHub's merge API with `sha` = H. A push git rejects (B moved) is refused. The PR's tasks settle at once, as a PR look would after the merge (#100's path), and their givers hear back, except the agent that called `merge`: it knows, so it gets no turn to be told (G159). Event `gathr.merge.done`; a refusal is the tool call's error. To try it without GitHub, `GATHR_GH_PATH` names a stand-in for `gh` in dev and tests: `examples/fake_gh.rs` answers from the JSON file `GATHR_FAKE_GH` names (an answer's `outs` in turn, or `out_merged` once its `merged_if` head is in that base in a local repository) and logs each call beside it (`tests/merge.rs`).
