# The API: checks runs and merging

Part of [AGENTS.md](../AGENTS.md)'s Run, use and check it; the other parts are listed there. The API's address and sign-in are in [api.md](api.md).

- Review evidence (G165): a CI wake on a review task keeps its recorded done review. R covers H when they are equal, or every added first-parent commit is a two-parent merge whose first parent is the preceding accepted commit and whose other parent is on the fetched base. Each whole tree must match Git's clean automatic merge (`git merge-tree --write-tree`); author changes, conflicts and unsupported merge shapes need review again. Current-head checks still gate the merge. An explicit unfinished finish, cancellation or restart withdraws approval. A held review's owner can re-record done on that same task without changing its PR, dependencies or lifecycle. Upgrade preserves provably completed reviews; an ambiguous older held record needs that explicit refresh.

- Checks runs (0043 C3): Gathr runs a project's checks (C2b) at a commit in `<agent folder>/<Project>/checks`, a detached worktree of the project reset before each run (`fetch` from `origin`, `checkout --force`, `clean -ffdx`), so nothing left uncommitted anywhere, nor by an earlier run, reaches it. Caches are beside it in `<Project>/caches` (`CARGO_TARGET_DIR`, `npm_config_cache`, `PIP_CACHE_DIR`). One run at a time per project; commands run in order in `sh` (Git Bash on Windows), up to an hour each, stopping at the first failure. The PR looks start a run for an open review task's PR at each head they see that has none. `POST /api/projects/<id>/checks/runs {"head"}` starts one (409 for a project with no checks); `GET` lists the newest 50 (`?head=<commit>`: that commit's, however old), each with `head`, `state` (`running`, `passed`, `failed`), `why`, `ref` once failed, and `steps` (`command`, `exit`, `duration_ms`, the last 64 KB of `log`). `GET /api/projects/<id>/caches` answers `bytes`; `DELETE` removes them. A step whose result isn't saved fails the run (never a pass without its evidence). A run a stop of the service cut off ends failed at the next start, with its own `gathr.checks.end` so its reference traces, and doesn't count as run, so the PR looks run that commit again. Caches no run used for 14 days go with the service's looks (`GATHR_STALE_DAY_MS` shortens a day). Live `{"type": "checks", "project", "head", "run", "state"}`; events `gathr.checks.start`, `gathr.checks.end` (an error with why when it fails, so its reference traces) and `gathr.checks.caches`. Each task with a PR has `pr_head`, the head the PR looks last saw, so the window shows the run at that commit on the task: Summary's task list and a hand-off line's Open task open the task in the Tasks tab (owner's pick, room task 70), and Settings > Projects > Checks & merge shows the cache's size and Clear. Without GitHub, write a task's `pr_head` and the project's checks with the service stopped, then `POST …/checks/runs`.
- Merging (0043 C4): agents don't merge; a PR's reviewer calls `merge {"pr", "signed_off"}`, and Gathr refuses, with a reference, unless the caller owns a review of that PR in the chat recorded done on a commit R covering its head H (GitHub's `headRefOid`; the reviewed id, 7 to 40 hex characters, resolved in the project and a true prefix of R), the checks the project asks for passed on H (`ci`: GitHub's `statusCheckRollup`; `gathr`: the latest checks run at H passed, C3, and started after the checks were last set; `both`; `none`: no checks, the review alone, 0045), and the default branch's B (fetched from `origin`) is in H. The PR's head and base are read again just before the push and refused if either changed; after it, the tasks settle only once GitHub shows the PR merged at that head into that base (waiting up to 20 s, `GATHR_MERGE_CONFIRM_MS` shortens it in dev and tests), else the answer says it isn't shown merged, with a reference, and nothing settles; settling that fails after the merge is said the same way, and the PR looks settle the tasks once GitHub reports the merge. A PR changing tests or check settings (a `test`/`spec` path, `.github/workflows/`, `package.json`, `Cargo.toml`, `pyproject.toml` and the like), or bringing a project its first passing checks on main (no passed run at B or before it), also needs `signed_off: true`. One merge per repository at a time, by the project's `merge`: `fast-forward` pushes H to the base, `merge` pushes a merge commit of H onto B made with `git commit-tree` (as the checkout's own git user), `squash` calls GitHub's merge API with `sha` = H. A push git rejects (B moved) is refused. The PR's tasks settle at once, as a PR look would after the merge (#100's path), and their givers hear back, except the agent that called `merge`: it knows, so it gets no turn to be told (G159). Event `gathr.merge.done`; a refusal is the tool call's error. Once GitHub confirms it, the merge brings the project folder along ([0067](decisions/0067-a-merge-brings-the-project-folder-along.md)): it fetches `origin` again (a squash is made on GitHub) and runs `git merge --ff-only --no-autostash origin/<base>` in the folder when the PR's base is `origin`'s default branch (`git ls-remote --symref`), no merge, rebase or cherry-pick is under way, the folder is on that branch and has no commits `origin` doesn't. Otherwise, or when git refuses (a changed file the merge touches, named from `git diff --name-only`), the folder is left as it is and Gathr says one line in the chat, in no turn: `Merged #5, but didn't update the project folder: <why>. Update it yourself with git pull --ff-only once it's safe. (ref <merge's reference>)`. Event `gathr.merge.checkout` (`pr`, `base`, `commit`; an error `fetch`, `default`, `not_default`, `under_way`, `branch`, `local_commits` or `refused`, with why). The merge's answer doesn't change. Sign-off said with the review (`finish_task`'s `signed_off`, below) counts as `signed_off: true`. To try it without GitHub, `GATHR_GH_PATH` names a stand-in for `gh` in dev and tests: `examples/fake_gh.rs` answers from the JSON file `GATHR_FAKE_GH` names (an answer's `outs` in turn, `out_merged` once its `merged_if` head is in that base in a local repository, or a real squash commit on a local repository with `squash`) and logs each call beside it (`tests/merge.rs`).
- Landing ([0049](decisions/0049-gathr-lands-pull-requests.md)): a clean review is the word to land. Gathr merges a PR of a project's chat, with the merge tool's own code and no agent's turn, once the newest review of it in the chat that isn't cancelled is done on a commit covering its head, the PR is open into the default branch (asked of `origin` with `git ls-remote --symref`) and up to date with it, what the project requires passed on the head, no CI run is still going there whatever it requires (each check as `gh pr view`'s `statusCheckRollup` gives it), and its reviewer signed off where `merge` would ask: `finish_task {"how": "done", "commit", "signed_off": true}`, kept on the review (`signed_off` on its task) while that review stands, and taken on the same done review reported again. Gathr looks when a review is reported done (in that call: the answer says what it did or saw, such as `Merged #5's 0123456 into main (merge): its tasks are settled.` or `Gathr lands #5 by itself. Now: CI is still going on 0123456 (running: UI (macOS)).`), when a checks run ends, after each merge, and at each of the service's looks at tasks' PRs; one repository at a time, the PR whose review came clean first first. A PR behind its base is brought up to date as `update_pr` does, once for that head and only the first in line; the reviewer is told if the head hasn't moved 5 minutes on. Whatever else stops it wakes its reviewer once for that head, on no task, with what Gathr saw (`Gathr can't land #5 at 0123456: …`): a failed update, a required check that failed, was cancelled or never ran, a CI failure the project doesn't require (a cancelled job isn't one), missing sign-off, a base that isn't the default branch, a fork's PR (GitHub's `isCrossRepository`, even with its head fetched into the project), a merge that was refused. Its review stands, and when its own report had Gathr look, the answer says it and no turn follows. A review that doesn't reach the head wakes nobody, whatever else is wrong with the PR. `landings` keeps, for each chat's PR at each head, that Gathr asked for the update, told the reviewer, or pushed a merge GitHub didn't confirm, so none is done twice across looks, two looks at once and a restart. A pause of the app or the chat holds landing. Events: `gathr.merge.done` and `gathr.github.update` with `landed: true`, `gathr.land.told` (`pr`, `head`, `why`, `woken`), and `gathr.land.look` when a look couldn't be made (once while it lasts, with why). To try it without GitHub: as in `tests/merge/lands.rs`.
- The far end ([0054](decisions/0054-a-change-past-the-far-end-waits-for-the-person.md)): landing and the merge tool measure a PR before the sign-off, once the review covers the head: `git diff --numstat --no-renames -z <base>...<head>` (the sign-off's changed files are read from it) leaving out binary files, lock files and the paths `git check-attr --source=<base>` marks (the checkout's own attributes with a git older than 2.40) `linguist-generated` or `linguist-vendored`; the line is the most any of the base's last 50 first-parent commits added by the same count, never under 3,000 (3,000 under 10 commits), kept in memory for each project and base. `changes` keeps, for each project's PR, the head, count (`counted`, `removed`, `top`) and line, written only at a new head or line (`gathr.change.measured`, with `by`: `landing` or `merge`). A PR over the line, and over the count the person let through plus the line, rests on Gathr's question to the person ([api-tasks.md](api-tasks.md)): landing says `waits on the person's answer to #<n>`, and `merge` refuses with `#5 waits on the person's answer to #<n>` and a reference. A head the person sent back rests too (`was sent back by the person at <short commit>`), and a question they cancelled rests the PR until a new head (`waits on a new head: the person cancelled #<n>`). A diff or `check-attr` that fails takes the path a failed diff took in the sign-off (`gathr.land.look` or the tool's error, with a reference) and writes no row. A PR seen merged or closed (a look, or `settle` after Gathr's own merge) ends its question. Closed removes the row (`gathr.change.closed`). Merged fills it as the record: builder and reviewer with their engine and model, `unasked` notes, `first_reviewed`, `by_gathr` (marked when Gathr's push succeeds, so a merge a look sees first or GitHub confirms late is still Gathr's) and `landed_ts` (`gathr.change.landed`; `gathr.change.merged_unasked` and `gathr.change.merged_sent_back` when it merged with the question open or at a sent-back head; `gathr.change.withdrawn` and `gathr.change.answered` as in api-tasks.md). The line is the lower of the project's and the PR's work task's (a Fix's, or its part's: [api-tasks.md](api-tasks.md), [0064](decisions/0064-a-change-far-past-its-fix-or-its-part-stops-and-asks.md)); the work task is the PR's earliest one that isn't cancelled, and a task with no line leaves the project's. The row's `line_of` says which it was measured against (`project`, `fix` or `part`; rows from before migration 0050 read `project`) and the question's words follow it. The same count is made, with the task's line, when a building task reports the PR done (`gathr.change.measured` with `by` `report`; a count kept at the same head and line isn't made again, and landing reuses it), and what the person let through then holds at landing. `changes.size` is the size of the ask the PR's work task answered, `repair`, `new` or null, written when the row is filled at the merge (`gathr.change.landed` carries it as `gathr.ask.size`); a Fix's line reads it. A failure of that write is `gathr.change.ended` with an error. Deleting an archived chat keeps its landed rows. Not built: a measure in the PR looks, and holds on turns ([0054](decisions/0054-a-change-past-the-far-end-waits-for-the-person.md#left-out-on-the-owners-word)).
