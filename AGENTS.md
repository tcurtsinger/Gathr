# Gathr

Gathr is an open-source desktop app for running a team of AI agents from different providers (Claude Code, Codex and more) on your own computer: chats, rooms where agents work together, tasks, plans and reviews, with logging and analytics built in, so you can see how the agents work and make it better.

Status: early. Product, design and architecture come first; see `docs/`.

## How we build

- **Plans before code.** Nothing is built until its plan is approved. Each decision gets a file in `docs/decisions/`: the choice, why, and what was turned down.
- **One feature, one PR,** its engine and its screens together, opened when the feature is done. From your own branch and your own git worktree (never the main checkout), base `main`, marked ready. Don't stack a PR on another PR's branch: merging that branch closes it.
- **Every change that can break has its check:** a test, or a command anyone can run that fails if the change breaks.
- **Tests where they earn it, not one per function.** Test behaviour that can go wrong: logic with branches, parsers and protocols (an engine driver against replayed raw frames), coordination state and its transitions, logins, security and data that could be lost, and every bug fixed (its test first). Don't test what can't really break: plain glue, getters, constants, what the type system already guarantees, or a layout a screenshot proves. One test per behaviour, through the real code where it's cheap, not mocks of our own code. A test that can't fail is deleted. Tests are written test first, at the seams the plan names: read [docs/testing.md](docs/testing.md) before the first test of a change.
- **Tests:** CI is the gate. The author runs the tests the change touches once before pushing; the reviewer reads and doesn't rerun suites.
- **Review once, when it's ready.** The code reviewer reviews every PR. The author answers each note; a second look only for a fix that changes behaviour. Minor notes are fixed in passing or dropped, never a round of their own. A docs-only PR merges without review rounds unless something in it is wrong.
- **The reviewer merges** once their review (or second look) is clean, the notes are answered and CI is green on the head they reviewed, with a merge commit: `gh pr merge --merge --delete-branch --match-head-commit <full head commit SHA>`. Nobody turns on auto-merge. A PR must be up to date with `main` before it merges (`gh pr update-branch <n>`, then CI on the new head; a head that only brings in `main` needs no new review). A docs-only PR is merged by its author on green CI. When the lead says PRs must land in an order, the reviewer keeps it. After a merge, the merger brings the owner's main checkout up to date (below). Check `main` is green before opening the next PR.
- **Clean up after yourself:** once your PR is merged or closed, remove your worktree and branch.
- **Keep this file current:** when a step here changes, or you learn one, change this file in the same PR.

## Build and check

- **Toolchain:** Rust through [rustup](https://rustup.rs); `rust-toolchain.toml` pins the version, so `cargo` picks it up by itself. The UI in `ui/` uses Node 24 (`ui/.node-version`) and npm: run `npm ci` in `ui/` once, and again when `package-lock.json` changes.
- **The checks CI runs**, from the repo root (run them once before pushing):
  - `cargo fmt --all --check`
  - `cargo clippy --workspace --all-targets --locked -- -D warnings`
  - `cargo test --workspace --locked`. A failing test that started a service prints the service's last 50 events, and with `GATHR_TEST_KEEP=<folder>` set keeps a copy of its data folder there; in CI, a failed Rust job keeps them as the artifact `rust-failures-<Windows|macOS>`. A request that times out names itself, how long it waited and how many bytes came back.
  - `bash scripts/check-file-size.sh` (source files up to 1,000 lines, lines up to 200 characters). Stage new source files first: this check reads `git ls-files`.
  - `node scripts/scrub-frames.check.mjs` (a recording's scrub keeps the person's own names out)
  - `node scripts/registry.check.mjs` (the files in `ui/src/registry` are as published, [0030](docs/decisions/0030-ui-foundation.md))
  - in `ui/`: `npx biome ci`, `npx tsc --noEmit`, `npx vitest run`, `npx vite build`. The tests run in a real browser: Edge on Windows (already installed), WebKit on macOS (`npx playwright install webkit` once). A failing test leaves its screenshot in `ui/.vitest/`; in CI, a failed UI job keeps that folder as the artifact `ui-failures-<Windows|macOS>`.
- **UI tests rendering registry controls** import `ui/src/theme.css`, as the app entry does. Without it, unstyled tooltips can cover menu items in WebKit; a pointer failure must be checked against the saved screenshot and click log. Its font arrives by swap, so `ui/src/fonts.setup.ts` loads it before each file's tests: a swap mid-test moved text a test measured.
- **CI** is `.github/workflows/ci.yml`, on Windows and macOS, for every PR and every push to `main`. `main` only takes PRs with CI green.
- **Releases** (F7): `.github/workflows/release.yml` publishes a GitHub Release `v0.1.<run>` once CI passes on a push to `main`: the Windows installer (NSIS, per user, unsigned, so SmartScreen warns on a first install), the Mac `.dmg` (Apple Silicon, ad-hoc signed: a first open needs System Settings > Privacy & Security > Open Anyway), the window's update with `latest.json`, and the service's `gathrd-<version>-<target>.tar.gz` with `gathrd.json` (0031). Updates are signed with the updater's key, kept only as the GitHub secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (its public key is in `crates/gathr-app/tauri.conf.json`). The version is written into `Cargo.toml` in CI only. A PR that changes `release.yml`, `scripts/release.mjs` or `crates/gathr-app` builds the same files unpublished, as the artifact `release-0.1.<run>`, its window pointed at a feed on `127.0.0.1:47199`. Each step is `node scripts/release.mjs` (`stamp`, `sidecar`, `collect`, `feeds`), so a local build runs the same ones; the Tauri CLI is `ui/node_modules/.bin/tauri build --config crates/gathr-app/tauri.release.conf.json`, from the repo root.
- **On a Mac without Rust:** each macOS run keeps its build for 7 days as the artifact `gathr-macos` (`gh run download <run> -n gathr-macos`). Start `gathrd` in the Mac's login session, not an SSH shell: over SSH the Keychain is locked, so every account reads as signed out. From SSH, run it as a launchd job in that session (`launchctl bootstrap gui/$(id -u) <plist>`, with `RunAtLoad`), and `launchctl bootout` it after. To run it installed, download the same run's `gathr-ui` artifact too, as a folder named `ui` beside the binaries, and open `gathr-app` (no Node needed). For the dev window: copy the same commit's `ui/` and `designs/tokens.css` (the UI imports it) beside the build, keeping their folders, run `npm ci` in it, then from that folder `./gathr dev --port <port> --data <folder> --window` in Terminal (it uses the `ui` folder it's started in, as the build came from another computer).
- **Commit messages on Windows:** write the message to a file and use `git commit -F <file>`; the same for scripts, write them to a file and run that. Inline multi-line strings get mangled by the shell.
- **PR screenshots:** attach them with `gh pr edit <n> --attach <file>`.
- **Flaky is broken.** A test that fails at random is fixed or deleted the day it's seen, never rerun until green. A failing test says which test it is, what it expected and what it got ([docs/testing.md](docs/testing.md)).

## Run, use and check it

- **The crate:** `crates/gathr` holds the shared library and two binaries: `gathrd`, the service, and `gathr`, the command line. Service code is in `src/bin/gathrd/`, command-line code in `src/bin/gathr/`, and what both use in `src/`.
- **Start it with test data:** `cargo dev --port <port> --data <folder> --seed` builds both, adds the made-up chats (500 messages, 50 tool calls in a turn, a 20,000-word answer, and a team of five over 20 rounds: tasks, hear-backs, reviews and a late reply, on a made-up account "Seed team", and six open questions for the person across two chats, one of each answer form, three with files) and starts the service. Ctrl+C stops it and everything it started. `cargo dev` and `gathr seed` refuse to run without `--data`, so made-up data never reaches the installed Gathr's own folder. Its agent folder is beside the data folder, `<data>-agents`, as for every data folder but the system's own, so made-up projects never reach the person's own `~/Gathr`.
- **With the window:** add `--window` to `cargo dev`: it also starts the UI's dev server on the port plus 10 and the desktop window on it, and Ctrl+C stops them too. A browser can open the same address (`http://127.0.0.1:<port + 10>/`). The dev server adds the service's token to every `/api` request, so the page never holds it. Its window's title says `Gathr (dev <port>)`.
- **Chats and projects in the window:** New (or a project's + in the sidebar) opens a draft, and the chat is made at its first send, in the project picked above the composer. New project, last in that picker, takes a name, a git folder and up to 5 agents with their roles. A chat with more than one member shows Summary and the team chat beside the Supervisor's (the header's Show/Hide team chat, kept per chat), the Supervisor's current round as Plan above the composer (the tasks of its newest hand-off, by `given_in`), and its recipient picker lists the Supervisor first; to see a round without a login, give tasks through the tools with the replay engine held, as in Tasks and waits below. The replay engine plays its recording once per process and Gathr reuses an engine for an agent's next turn, so for several turns repeat the recording's rows once per turn.
- **Archive, Delete and stale in the window:** the chat header's More menu and each sidebar row's have Archive (Restore once archived) and Delete, each asked first. Archived chats are in the folded Archived group at the foot of the sidebar and open read only, with Restore. The Tasks list groups stale ones under Stale; an agent's stale task opens in its chat's Tasks tab with Cancel and Restart. To see stale tasks on test data, start the service with `GATHR_STALE_DAY_MS=15000` and `GATHR_WAIT_EVERY_MS=2000`: the seed's open tasks go stale in about a minute. Settings > General has the two day counts.
- **Search in the window:** Search under New, or Ctrl K (Cmd K on macOS), searches chat titles and saved messages across chats (0035); the query stays between openings. Up and Down move one cursor over Chats then Messages, Enter opens the row. A message hit opens its chat centred on that message (the team column opens for a member's), tinted briefly and focused, and the view holds there until the person scrolls back to the bottom or sends: `gathr.ui.search.open` times it, `gathr.ui.search.error` records a failed search with its `ref` or a hit no longer in its chat. Seeded text repeats about 40 words, so every long message matches most queries: to try a hit far up a chat, add a distinctive word to one message in a stopped test folder's database (the index follows an `UPDATE` of `body`).
- **Pause and stop in the window:** the chat header's More menu has Pause, then Resume, or Restart after a stop; the composer's Stop while a turn runs is Stop now for the chat. Each agent's row in Summary has its own More menu, and the tray has Pause all and Resume all. While paused or stopped, a quiet line after the latest message says so. The replay engine takes an interrupt only while it streams, so to try Stop now on a held round, let it stream first.
- **The person's questions in the window:** Tasks under New lists every open question across chats (`--seed` adds six; seed a folder several times for dozens). Picking one opens its chat's workspace (the header's sidebar toggle) at that question in the Tasks tab: Back and Next keep drafts, Send on the last sends every ready answer, and a refused one stays open with its reference. A question's file opens as a tab beside Tasks. To force a refusal, block a window's live socket, cancel the question with `POST /api/tasks/<n>/cancel`, then Send it there.
- **Without a login:** `examples/replay_engine.rs` stands in for Claude Code. Build it (`cargo build --example replay_engine`), start `cargo dev` with `GATHR_REPLAY` set to a recording in `crates/gathr/tests/frames` and `GATHR_CLAUDE_PATH` set to `target/debug/examples/replay_engine(.exe)`, add an account (`POST /api/accounts`), and put a made-up `.credentials.json` with an `accessToken` and `refreshToken` in its `<data>/accounts/<id>/claude`. Every send then plays that recording. A `{"dir": "sleep", "line": "<ms>"}` row in a recording pauses that long, for a stream at a real pace when timing.
- **Run it installed, without cargo or a dev server:** put `gathr-app`, `gathrd` and the built UI (`npx vite build` in `ui/`, then `ui/dist` copied as a folder named `ui`) in one folder, and open `gathr-app`. With no arguments it uses the system's app data folder (`--data <folder>` for a check), finds the service there or starts it, and signs in through a one-time link. The service runs from the data folder's own copy, `<data>/app/<version>/gathrd` with its `ui`, copied from beside `gathr-app` at first start and again when the installed one is newer or rebuilt ([0032](docs/decisions/0032-service-updates.md)). `gathrd` serves the UI from the `ui` folder beside it (`--ui <folder>` for another). Closing the window hides it in the tray (the menu bar on macOS) and the service keeps running; opening Gathr again on the same data folder shows that window, starting the service again if it stopped. Quit in the tray stops both. Each data folder has its own window, so a check on a test folder never brings up the owner's. A service started this way never sees a `GATHR_*` variable, and one started with no `--port` never keeps a port from 47100 to 47114.
- **The window's title bar follows Theme** (Settings > General): the page calls the window's `set_theme`, the one command its IPC allows, and only from `http://127.0.0.1` (`crates/gathr-app/capabilities/theme.json`); a refusal is a `gathr.ui.window.theme` error. To check System, drive the window without `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port`: with it, the page always reads the system as light.
- **The window updates itself** (F7): a release build checks `latest.json` at start and every hour, downloads the update and checks its signature, then installs it at once if the window is hidden in the tray, else when it's next hidden; meanwhile the tray menu has Restart to update. Only the window restarts, hidden again if it was; the service keeps running. When the service hands over to its own update, the window signs in to the new one by itself (`gathr.ui.window.follow`); when the service stops answering for 3 s while the window is open, the window starts it again the way a launch does, so a new copy that died on trial rolls back at once (`gathr.ui.window.restart`; a failed restart goes to the crash log). A window showing Start failed tries the same every 3 s, so it takes up a folder an old service let go of without a relaunch; to check, hold `<data>/gathrd.lock` from another process while it opens, then release it. To stop a test service for good, quit or stop the window first. A debug build never checks. Events are `gathr.ui.update.check` and `gathr.ui.update.install`. To try one locally: build two versions with `release.mjs` and the Tauri CLI, adding a `--config` whose `plugins.updater` has your own test key's `pubkey`, `endpoints` `["http://127.0.0.1:47199/latest.json"]` and `dangerousInsecureTransportProtocol: true` (sign with that key in `TAURI_SIGNING_PRIVATE_KEY`, never the real one), with `GATHR_APP_FEED=http://127.0.0.1:47199` set so the service checks the same feed; serve the newer one's folder after `release.mjs feeds <version> <folder> http://127.0.0.1:47199` on that port; install the older one with `<setup>.exe /S /D=<folder>` (it also adds a desktop shortcut: delete it, and run `uninstall.exe /S` when done), and open it with `--data`. A PR's build artifact does the same with the real key.
- **A browser on the service itself:** `gathr open --data <folder>` starts the service if it isn't running and prints a link that signs a browser in once (good for 60 s). On Windows, a service it starts inherits its output: send that output to a file, not a pipe you wait on.
- **Test data alone:** `gathr seed --data <folder>`, with the service stopped. Each run adds another set, so repeated runs make a large folder for timings.
- **Diagnose with `gathr diag`** (`target/debug/gathr` once built, or `cargo run -q --bin gathr --`), always with `--data <folder>`. JSON by default, `--text` to read:
  - `diag health`: the service now, the database, the last start-up check and the crash log. It answers even when the service or the database won't start.
  - `diag trace <ref>`: everything behind an error's reference, in order.
  - `diag failures --since 24h`: failures grouped by cause, with references.
  - `diag query "<sql>"`: read-only SQL, up to 1,000 rows. Use the `event_log` view: it shows `attrs` as JSON, a readable `time` and each row's `ref`.
  - `diag turn <ref> --raw`: the turns behind a reference, with every engine frame in and out of each, redacted.
  - `diag bundle`: health, a day's failures, recent events and engine frames (no bodies) in one file under `<data>/bundles`.
  - `diag health` also shows each account's sign-in state, and the messages held on the chats' account.
- **The API** is on `127.0.0.1:<port>`. Every `/api` request needs `Authorization: Bearer <token>`, with the token from `<data>/service.json`, or the browser's cookie `gathr-<port>`: `POST /api/once` gives a code, and opening `/?once=<code>` swaps it for the cookie (HTTP-only, `SameSite=Strict`, new at each start of the service). Other paths serve the built UI. Errors answer `{"error": "… failed", "why", "ref"}`, and each is recorded before the answer goes out, so its `ref` traces at once.
  - Chats: `GET`/`POST /api/chats` (`?archived=true` lists the archived ones instead, each with `archived`), `GET /api/chats/<id>` (messages in their turns' order, each with its `agent`; turns, each with its `task` and the turn it `answers`; `project` and `folder`; `members`; open `approvals`; `streaming`, each agent's reply text not saved yet), `POST /api/chats/<id>/messages {"text", "agent"}` (as that agent; with none, on the oldest account). An agent runs one turn at a time across its chats, with its own engine session in each chat, so a message for a busy agent answers `queued`. `POST /api/chats/<id>/stop` (the chat's turns, whichever agent they're for), `POST /api/chats/<id>/approvals/<request_id> {"allow"}`.
  - Team chats ([0028](docs/decisions/0028-team-chats.md)): `POST /api/chats {"members": [{"agent", "role"}]}` (`supervisor`, `reviewer`, `member`) or `{"project"}` (copies the project's folder and team), `PATCH /api/chats/<id> {"members"}` replaces the whole list; `{"project"}` puts a chat with no messages yet in a project (409 once it has some). A message goes to its `agent`, else the first member its text names with `@Name`, else the Supervisor. In a chat with no project, an `agent` from outside joins it (the agent so far becomes Supervisor); in a project chat it must be one of the chat's.
  - Projects: `GET /api/projects` (`{"projects": [...]}`), `POST /api/projects {"name", "folder", "members"}` (names unique ignoring case; the folder a full path in a git repository). In a project chat each agent's engine runs in its own worktree, in its folder in the agent folder (below), made at its first turn from the remote's default branch, fetched then. To try it without the network, make the project a local clone: its `origin` is the folder it was cloned from.
  - Engines and git get the person's current PATH: read again from the registry on Windows, from the login shell on macOS. The engine's start event says where it came from (`gathr.env.from`).
  - Gathr's own updates ([0032](docs/decisions/0032-service-updates.md)): `GET /api/app` (the version that runs, the one before, `state`, the last check, `failed` with its `ref`, `update` while it holds; live as `{"type": "app"}`), `POST /api/app/update` checks now. Each release's `gathrd.json` names its archive; `GATHR_APP_RELEASES` names another feed (a debug build has none), and `GATHR_APP_HOLD_MS` shortens the 30-minute hold, in dev and tests only. A build made with `GATHR_APP_FEED=<address>` set checks that feed instead of GitHub's, with no variable at run time: build a test release that way to try an update on an installed Gathr exactly as a real one runs. Events are `gathr.app.update`, `gathr.app.hold`, `gathr.app.switch` and `gathr.app.handover` (where the last hand-over got to, from `app/handover.json`). To force a stopped hand-over, write that file with a `step` other than `starting the update` in a stopped test folder, start it, and trace the reference `diag failures` gives. The replay engine's `GATHR_REPLAY_CHILD` leaves a child holding its output after the engine is killed, as in the 0.1.39 hang.
  - Codex models (0033): Engine default, Gathr-owned Family Latest rows, then exact models, all from the account's catalog. Latest IDs are `latest:<family>`; numeric `gpt-<version>-<lowercase family>` names group automatically, unfamiliar shapes stay exact. Each new engine session resolves the alias against all model-list pages before opening the thread.
  - Codex (0033): `GET /api/engines/codex` and `POST /api/engines/codex/update` match Claude's copy state. Its npm platform archive is SHA-512 checked, with the full `vendor/<target>` retained. `GATHR_CODEX_RELEASES` names another npm metadata feed in dev and tests; `GATHR_CODEX_PATH` stands in for the owned executable. A debug build downloads nothing unless a feed is set.
  - Claude Code: `GET /api/engines/claude` (where it was found, Gathr's copy). `POST /api/engines/claude/update` checks the release feed now. Settings has no path: `GATHR_CLAUDE_PATH` in the service's environment stands in for Gathr's copy, in dev and tests only (the replay engine, or a missing file for a forced failure).
  - Accounts: `GET /api/accounts`, `POST /api/accounts {"engine": "claude", "name"}`, `GET /api/accounts/<id>`, `PATCH /api/accounts/<id> {"name"}`, `DELETE /api/accounts/<id>` (signs it out, closes its engines gently and deletes its folder; one that reads signed out needs no Claude Code, and on macOS with no Claude Code the sign-in state is its Keychain item). Names are unique, ignoring case. Each account's login is in `<data>/accounts/<id>/claude`. A new data folder has no accounts; a message sent to no agent runs on the oldest one.
  - Codex accounts: add with `{"engine": "codex", "name"}`. Each owns `<data>/accounts/<id>/codex` as its `CODEX_HOME`, never the person's `~/.codex`. The same sign-in route starts the browser by default; `{"device": true}` starts a device code (beta, enabled in ChatGPT first). Both finish through `account/login/completed`, with `paste: false`; Claude sends `paste: true`. `BROWSER` names a test program when a real browser must not open. The replay engine enters Codex mode for `app-server`: `fail-login` in the account's Codex folder forces a failure, `hold-login` holds it for switching/cancelling. Remove either file after the check.
  - Models: `GET /api/accounts/<id>/models` lists the account's models (`id`, `resolved`, `latest`, `name`, `description`, `efforts`) as its engine reports them; `latest` marks a family alias such as `opus`, which moves to each new release. The replay engine answers with `tests/frames/initialize.json`.
  - Agents: `GET`/`POST /api/agents {"name", "account", "model", "effort", "approvals"}`, `GET`/`PATCH`/`DELETE /api/agents/<id>`. A `null` model or effort is the engine's default; one the account's engine doesn't list is refused. A new account clears the model and effort the same change doesn't set. A change applies from the agent's next turn. An account isn't removed while agents use it (409). Each agent shows `hold` (`why`, `pid`, `since_us`) while its engine hasn't exited 30 s after a gentle close; the live socket sends `{"type": "hold"}` when it starts and ends.
  - Engine times: an engine closes the gentle way to switch chats, accounts, model or effort, and after 10 idle minutes; it's never killed except at shutdown. `GATHR_HOLD_AFTER_MS` and `GATHR_IDLE_CLOSE_MS` in the service's environment shorten the 30 s hold and the 10 minutes, in dev and tests only.
  - Sign in: `POST /api/accounts/<id>/sign-in` runs `claude auth login` in the account's folder and answers its page's `url`; `POST …/sign-in/code {"code"}` passes a pasted code; `DELETE …/sign-in` cancels. `POST /api/accounts/<id>/sign-out` runs `claude auth logout` there. The replay engine answers both for Claude: `made-up-code#…` signs in, any other code fails. To keep a real run from opening your browser, set `BROWSER` to a script that only logs its argument. Without it, links open through the system (`rundll32 url.dll,FileProtocolHandler` on Windows, never `explorer.exe`, `open` on macOS): `cargo test -p gathr --test open_browser -- --ignored` checks a long sign-in link reaches the real browser whole (it opens a tab).
  - Approvals ([0029](docs/decisions/0029-approvals.md)): an agent's `approvals` is `ask`, `edits`, `auto` (the default) or `full`, Claude Code's Manual, `acceptEdits`, `auto` and `bypassPermissions`. In every mode but `full`, Claude Code asks Gathr's hook at `/hook` (the engine's own token only) before each file write and command, and it answers "ask" for a push command that may force, delete or skip the push hook, a file write outside the agent's folders (the one it runs in, its own and its project's Shared; links followed), or a `wait` with a check, which Gathr runs itself: `gathr.approvals.ask`. Every `git push` from an agent's worktree also goes through git's `pre-push` hook (in `<data>/hooks/<chat>/<agent>`, set as that worktree's own `core.hooksPath`), which sends its refs to `/hook/push` with `GATHR_AGENT_TOKEN` and `GATHR_PUSH_URL`: a push to the remote's default branch, a force push, a branch deletion or a push to anywhere but the worktree's `origin` waits as an approval named `git push`, saying why; any other push goes through (the owner's "Ask only for risky pushes"). Either way it's `gathr.approvals.push`, an ordinary one with `allowed_by`. To push by hand as an engine, run git in the worktree with those two variables from the replay engine's `GATHR_REPLAY_ENV` file. A block by auto mode's own check is `gathr.approvals.blocked`; an engine that started in another mode (auto isn't offered for every model) is a `gathr.approvals.mode` error. To try it live, point the test project's push URL at a bare repo first (`git remote set-url --push origin <bare>`), so an approval allowed by mistake never pushes anywhere real.
  - Gathr's tools: an MCP server at `/mcp` (Streamable HTTP) that takes only a running engine's own token, never the service's. Each engine gets one in `GATHR_AGENT_TOKEN`, and it ends when the engine exits; a tool acts as that engine's agent in its chat, and each call is a `gathr.tool.call` event on the turn's trace. Tools: `read_chat`, and for tasks and waits `give_task`, `finish_task`, `list_tasks`, `cancel_task`, `restart_task`, `wait`, `end_wait`, and `ask_person` for anything an agent needs from the person. A refusal answers `<tool> failed: <why> (ref …)`. Each engine's briefing is a file in `<data>/briefings` while it runs, and each turn's `invoke_agent` start event records what Gathr gave it (`gathr.context.briefing.chars`, `gathr.context.ask.chars`, each with a `tokens_estimate`, and `gathr.tools.off`); a message sent into the turn adds its size on a `gathr.turn.read` event when the engine reads it, and Diagnostics shows the sum. To call the tools by hand, run the replay engine with `GATHR_REPLAY_ENV` set to a file: each start appends its token there.

It starts `gathr-app` with `--hidden`, so Gathr opens in the tray: the one beside the service, else the one beside the installed `gathrd` the window last opened the folder from (`<data>/app/installed`), as the service runs from the folder's copy. A test folder's entry has its own name and its `--data`, never the person's own: turn it off when the check is done.
  - Tasks and waits ([0010](docs/decisions/0010-coordination-as-state.md)): agents give and settle them only through the tools above. `GET /api/chats/<id>/tasks` lists the chat's tasks (each with `given_in`, the turn that gave it) and its waits; `POST /api/tasks/<n>/cancel {"why"}` and `POST /api/tasks/<n>/restart` are the person's. Each turn in `GET /api/chats/<id>` carries its `task`, and what Gathr told an agent (a task, a wake-up, a hear-back) is a message with role `gathr`. The service looks at open CI, PR and check waits, and tasks' PRs, every 2 minutes; `GATHR_WAIT_EVERY_MS` in the service's environment shortens that, in dev and tests only. `gathr diag health` lists open tasks and waits; events are `gathr.task.*` and `gathr.wait.*`. To try it without a login, hold the replay engine (`GATHR_REPLAY_HOLD`), take a token from `GATHR_REPLAY_ENV`, and call the tools as in `tests/coordination.rs`.

A person task has `owner: null`, kind `person`, a `form` (`done`, `yesno`, `choice`, `choices`, `text`), `choices` (`label`, `detail`; the asker's pick first) and `files` (copies made when asked, read at `GET /api/tasks/<n>/files/<i>`, served with `Content-Security-Policy: sandbox`). `GET /api/person-tasks` (`?chat=<id>` for one chat) lists the open ones, oldest first, each with `chat_title` and `for_agent`; `POST /api/person-tasks/answer {"answers": [{"task", "pick", "yes", "done", "text"}]}` takes each answer or refuses it on its own (`{"answered", "refused": [{"task", "why", "ref"}]}`); words alone answer any form. Each Send wakes each asker once (`gathr.task.answered`); a refusal is `gathr.task.answer`.
  - Pause and stop (F10, [0010](docs/decisions/0010-coordination-as-state.md)): `GET /api/pauses` lists each pause (`scope` `app`, `chat` or `agent`, its `target` id, `since_us`, `state` `pausing` while a turn, background command or wait check in it still runs, then `paused`, or `stopped` after Stop now, and what still `running`) and each account's usage hold (`until_us`, `kind`, its `agents`). `POST /api/pauses {"scope", "target"}` pauses; `POST /api/pauses/resume` resumes, which is Restart after a stop; `POST /api/pauses/stop` is Stop now: it interrupts the scope's turns, ends their engines' background commands with Claude Code's own `stop_task`, and queues a carry-on per agent that waits for Restart. A pause holds the turns Gathr queues (tasks, wake-ups, hear-backs) and its waits' looks and checks, never the person's own message; a held turn stays `queued` with `held` (`pause` or `usage`) and its `why`, and all of it outlasts a restart. `GET /api/chats/<id>` adds `run` (the chat's own pause or the app's, else `{"state": "running"}`) and, on each member, `paused` and `usage_until_us`. A `rate_limit_event` with status `rejected` holds the account until 30 s after its reset: a turn that ran no tool is sent again then, one that did ends and a carry-on waits (`tests/frames/usage_limit.jsonl` is made by hand: no limit was hit live). When a background command ends, Claude Code starts a turn by itself: it gets its row, on the task of the turn that started the command, and a task stays `held` while one runs. An engine that exits takes its commands with it: a task held on them carries on. A turn with no progress for 10 minutes (20 during a tool) is flagged once (`gathr.turn.stalled`, live `{"type": "stalled"}`), never stopped; `GATHR_STALL_AFTER_MS` shortens that, in dev and tests only. Events are `gathr.pause.*` and `gathr.usage.hold`.

  - Archive and delete (F11, [0010](docs/decisions/0010-coordination-as-state.md)): `POST /api/chats/<id>/archive` ends the chat's work in one step (its open tasks cancelled with why, waits ended, queued turns stopped, its pause gone, one `gathr.chat.archive` event), then interrupts its running turns and ends their background commands; it answers `{"archived", "ended": {"tasks", "waits", "turns"}}`. A send, a task or a restart in an archived chat is refused (409, `the chat is archived`). `POST …/unarchive` puts it back in the list and starts nothing. `DELETE /api/chats/<id>` archives it first, closes its engines the gentle way, removes its rows, then its worktrees (their branches stay), hooks and task files: `{"deleted", "left"}`, `left` naming what couldn't be removed, with its reference. Archiving also removes the chat's worktrees in the agent folder (below), which a restored chat's next turn checks out again from their branches, but keeps a worktree with changes not committed, and a chat's folder outside a project, until the chat is deleted. Each sends `{"type": "chat", "chat", "change"}` live (`archived`, `unarchived`, `deleted`).
  - Stale tasks (F11): a task nothing moved for the stale days gets `stale_us` (its last move) and its Supervisor is told once; after the cancel days stale it's cancelled (`stale since <date>`, restartable) unless something can still move it. `GET /api/settings` and `PATCH /api/settings {"stale_days", "cancel_days", "agent_folder"}` (Settings > General, 1 to 365 each, 3 and 7 by default). `GET /api/person-tasks` adds `stale`, the agents' stale tasks across chats (each with `chat_title`). The sweep runs with the service's looks; `GATHR_STALE_DAY_MS` shortens a day, in dev and tests only. A task whose `after` task or blocker is cancelled is cancelled at once. Events are `gathr.task.stale`, `gathr.chat.*` and `gathr.settings.change`.

It applies to new work. Each project has `<agent folder>/<Project>/Shared` and `<Project>/<Agent>`, names made safe for both disks, unique, and kept across a rename (`folder_name`); a chat with no project uses `Chats`. An agent's worktree is `<Agent>/<chat>` (the chat id's last six characters), a plain chat's folder the same, and each engine's `TEMP`, `TMP` and `TMPDIR` is `<Agent>/temp/chat-<chat>`, fixed when it starts and cleared once it closes (never a restart to change it). Claude Code gets `--add-dir` for the agent's folder and Shared, Codex both as writable roots; one that holds the data folder or leads into it through a link isn't passed (`gathr.folder.refused`, with a reference), an agent folder that does (a link made after it was saved) fails the turn before anything is made, and the hook asks before any write that lands in the data folder, links followed, except in an engine's own folder from before the agent folder (`<data>/worktrees/<chat>/<agent>`, `<data>/chats/<chat>`) while no link in it leads elsewhere (one that does fails the turn the same way). Paths are as the disk names them (macOS's `/private/var`), so a test compares the engine's folders with `gathr::folders::real`. Every folder is recorded before it's made (`agent_folders`; the start event's `gathr.folder.*`); worktrees from before stay in `<data>/worktrees` for an agent with a session there. A sweep with the service's looks (and at once on archive and delete) removes a closed engine's temp folder, an archived chat's worktrees and a deleted chat's folders, never one a running engine or wait check uses, nor one whose chat was restored meanwhile: `gathr.cleanup.skip` (`in_use`, `changes`, `in_data`, `left`) with a reference, then `gathr.cleanup.remove` on the same trace. To try it: `cargo dev`, a project chat, a message; the start event's `cwd` is under `<data>-agents`; archive the chat and look for `gathr.cleanup.*` in `gathr diag failures` and `diag trace`.
  - Search ([0035](docs/decisions/0035-search.md)): `GET /api/search?q=<text>&archived=<bool>&limit=<n>` answers `{"chats", "messages"}`: up to 8 chats whose title holds `q` (`chat`, `title`, `project`, `archived`, `time` last active), then text messages holding every typed word as a word start, case and accents ignored, newest first (`limit` 30 by default, at most 100), each with `chat`, `chat_title`, `archived`, `message`, `role`, `agent`, `time`, `snippet` and `marks` (`[start, end]` in UTF-16 units). Archived chats are in, marked, unless `archived=false`. `q` is cut at 200 characters; an empty one finds nothing. Each request is a `gathr.search.query` event (`chars`, `words`, `chat_hits`, `message_hits`, `archived`, never the words). To time it, seed a folder 20 times (about 11k messages). To force a failure, drop `message_search` in a stopped test folder's database: the next search answers with a reference that `diag trace` finds.

## How the code is written

- **YAGNI.** The smallest code that gives the expected result. Before writing, climb the ladder and stop at the first rung that holds: does it need to exist; is it already in this codebase; does the standard library do it; does the platform (CSS, SQLite, the OS) do it; does a dependency we already have do it; does a known, trusted library made for the job do it (the owner OKs each new one); only then, the minimum new code. No abstraction with one user, no config for a value that never changes, nothing "for later".
- **Shared components, one of each.** One button, one scroll bar, one input, one menu, one dialog, one message, one empty state: each lives once in the shared UI code and the design system, and every screen uses it. A second version of something that exists is a bug in review, even if it looks the same. Same in the service: one way to do a thing (one error type per crate, one HTTP client, one way to spawn a process). The one exception: short programs (git, gh, a wait's check) start through `process-wrap` in `gathr::run`, so everything they start ends with them; engines start as they do and close the gentle way ([0031](docs/decisions/0031-short-programs-end-together.md)).
- **Registry files stay as published** ([0030](docs/decisions/0030-ui-foundation.md)). `ui/src/registry` holds the assistant-ui and shadcn registry files a merged screen uses, unchanged, each with its URL and sha256 in `ui/registry.json`. Gathr's code composes or wraps them from outside the folder. A change that must go inside is an adaptation: record its new hash and why in the same entry. Biome and the line limits skip the folder; the registry check holds it instead. Add a file only when a screen uses it.
- **Small files, readable lines.** Keep a file to what one part of the code does: usually a few hundred lines. CI fails a source file over 1,000 lines or any line over 200 characters (`scripts/check-file-size.sh`), so nothing grows into a monolith and nothing packed or minified is committed. Split a file where it has a seam, by what each part does. Small functions with one job.
- **Comments only where they earn it:** why something is done, a non-obvious constraint, a lesson ("never kill here: the engine may be renewing its login"). Never what the next line plainly does, never a comment on every function or field. Names carry the meaning.
- **Best practices of each language:** `rustfmt` and `clippy -D warnings` for Rust; for the UI, the linter and formatter that land with it. Errors handled where something can recover, passed up everywhere else. No dead code, no commented-out code.
- **Reviewers check all of this**, not only behaviour: a duplicate component, a file near the limit, a comment that restates the code, an abstraction nobody needs.

## How Gathr looks and reads

- **The design system wins over taste.** Design questions get two or three options, or mockups, before anything is built.
- **Copy follows [DESIGN.md: Copy](DESIGN.md#copy), including the owner's wording.** Use [JetBrains: Writing Short and Clear](https://plugins.jetbrains.com/docs/intellij/writing-short.html) for brevity, [Paste: Word list](https://paste-dsys.com/foundations/content/word-list/) for terms, and [Paste: Alert composition notes](https://paste-dsys.com/components/alert/#composition-notes) for notifications. Gathr terms take precedence. This applies to UI strings, accessible labels, Help, errors and Gathr-authored chat messages. Preserve identifiers, references, recovery steps and tool arguments. Agent instructions must remain clear enough to act on.
- **Every setting has a control in Settings.** Never "ask an agent" as the only way to change something.
- **One app, not one per screen.** A pattern that appears on more than one screen (messages, links, notices, buttons, empty states) lives in shared code and the design system, so every screen gets it. Something stays screen-specific only when that screen's job differs, and the design doc says why.
- **Agents are generic.** Never design a feature or its wording around one particular agent.

## Safety, sized to the risk

- **Guard only against real risks.** No kill switches, disabled features or disclaimers for their own sake. When a safety question comes up, check how Claude's and Codex's own apps handle it, and match that.
- **Diagnostics from the first attempt.** Anything that runs where nobody watches it (background work, installs, long jobs) writes what it did and where it stopped from day one.
- **Every feature is diagnosable** ([0019](docs/decisions/0019-troubleshooting.md)). Its events show in Diagnostics and `gathr diag`, every error it can show carries a reference, and its PR proves one forced failure found from that reference. Troubleshoot with `gathr diag` before reading files by hand.
- **No paid services required.** Gathr runs the providers' own agents on the user's own logins. Anything that costs money is an opt-in, off by default, and never required.
- **Logins are single-use secrets.** Each account's login lives in its own Gathr folder, never the person's own `~/.claude` or `~/.codex`. Agents on one account share its folder only through the renewal gate (`docs/decisions/0002-login-folders.md`). Never copy a login file, or force-kill an engine while it might be renewing its login.

## Rules for a public repo

- **Everything here is public.** No secrets, keys, tokens, `.env` files or login files, not even in tests or history. Never print a secret: check config and login files with counts or masked values.
- **No personal data:** no emails, addresses, IPs, device serials, employers, or screenshots of real conversations. Test data is made up. Commits use the owner's GitHub noreply address (git config already has it); check it before your first commit.
- **Reuse what we have the rights to.** Code the owner wrote can be referenced, adapted and ported freely. Code under a licence that doesn't allow reuse (see "Learning from SerenityOS" below) is for learning only: understand it, then write your own.
- **Dependencies:** well maintained, with a licence compatible with this repo's. Never add one for what a few lines can do.
